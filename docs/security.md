# Security model

- Public email registration validates names, email addresses and matching 12–72 character passwords; passwords use PHP's password API. Registration and sign-in are throttled. Google sign-in uses state and PKCE with a verified Google identity, and never silently links existing password accounts by email.
- The shared entry screen first checks an email through a CSRF-protected, IP-throttled request. Its next step is bound to that normalized email and a 15-minute server session, rather than a client-supplied account mode. Completing a different or expired selection is rejected and returns the browser to email entry. An existing account still requires its password or verified Google identity. The native HTML form follows the same flow without JavaScript.
- CSRF covers sign-in and all mutations. Session IDs regenerate on authentication, cookies are HTTP-only/SameSite=Lax, and secure cookies are enabled by default. Behind a TLS-terminating proxy, keep the public origin HTTPS and `SESSION_SECURE=true`; forwarded client-IP headers are not trusted for throttling.
- Sign-in fetches its current CSRF token from a same-origin, non-cacheable endpoint before submitting. An open form can recover after its session cookie expires; a failed refresh preserves the entered credentials and stops submission.
- Authentication uses database-backed active sessions and bounded inactivity. Remember tokens use random selectors, hashed validators, one-time consumption and rotation. Password changes revoke other sessions and remembered sign-ins.
- PDO uses native prepared statements. Ownership is checked for jobs, documents, applications, tasks, messages, providers and sources. Future multi-user routes must retain these checks.
- Sodium secretbox encrypts API keys and OAuth credentials using a unique environment key. Keys/tokens never appear in frontend HTML or JSON. Error logging excludes request bodies, external response bodies, credentials and exception messages that might include secrets.
- Uploads have request/MIME/size restrictions. Private filenames are random; path traversal is rejected. DOCX archives have file-count/expanded-size limits and disallow active content/DTDs/entities. No shell extraction is used. Original uploaded PDFs can contain arbitrary content: preview them with a current browser/PDF reader. Malware scanning is not bundled.
- Outbound HTTP allows public HTTPS on port 443 only, rejects private/reserved/shared/benchmark/documentation address ranges and embedded URL credentials, validates every resolved address, pins the chosen address, verifies TLS and refuses redirects. Deploy an outbound firewall as an additional network boundary.
- Robots directives are checked conservatively. Permission confirmation is required for sources and URL imports; it is not a substitute for source terms or authorisation. No login/CAPTCHA/anti-bot bypass is implemented.
- Untrusted advertisements/images/CV text are data in AI prompts. AI has no tools. JSON schemas, factual entry-index checks, verification gates and review keep model output from directly sending applications or inventing structured history. A model's prose is not independently proven factual: users must verify it.
- Budgets reserve estimated cost before requests under a user lock. Provider prices and vision reservations are supplied by the user; actual provider billing is external.
- API writes and expensive operations have account limits, and sign-in has an IP limit. Schedule pruning removes expired throttle/remember rows. There is no reverse-proxy trust assumption.
- Application sends require an approved verified package, known recipient, unexpired vacancy, enabled mode/method, daily capacity and a connected Gmail account. Automatic mode additionally requires eligibility and the configured score. All writes precede the external send reservation. Ambiguous sends are held, never automatically replayed.
- Serve only `Public/`, disable directory indexes, restrict `.env` permissions and back up the database/private files/encryption key together. Do not place production secrets in deployment examples or source archives.

This is a production-conscious baseline, not an independent penetration-test certification. Add deployment-specific monitoring, backups, retention, malware scanning and authentication controls according to your environment.

- SaaS data remains in one shared database, scoped by user ID. Incomplete accounts are routed through resumable onboarding unless they explicitly skip setup.
- Paid entitlements are checked on API requests, AI use, preparation, submission and worker execution. Monthly expiry is checked at use time. BYOK enables general AI tools without granting paid automation or CV features.
- The shared provider has an owner-controlled per-user budget, independent of user-editable preferences. Managed credentials cannot become personal connections without a replacement API key.
- M-Pesa prices are server-owned. Callback bodies cannot grant access: checkout-bound callbacks trigger an independent Daraja query, verified against both checkout and merchant request IDs. Settlement is transactional and idempotent. Sandbox cannot grant production membership.
- The M-Pesa callback is the only POST route exempt from browser CSRF. Unknown or invalid callback tokens are ignored. User-facing checkout/status requests remain authenticated, rate limited and CSRF protected.
- Reset snapshots, originals and encrypted provider configuration are private; backups live in ignored storage/run/backups with mode 0700. The database reset requires its configured database name and takes worker locks before removing user data.

- Inline Alpine components use the CSP runtime with a fresh per-response script nonce. The policy permits only same-origin libraries and nonce-authorised scripts, forbids native inline event handlers, and does not enable unsafe-inline or unsafe-eval. All user/model text is escaped or assigned through textContent, x-text or form-control values.
- Form submissions allow the application origin and `https://accounts.google.com`, so the CSRF-protected Google sign-in POST can redirect to Google's account chooser. Other external form destinations remain blocked.
- The shared Google callback dispatches Gmail only for a matching Gmail state in the current session. Gmail validates the authenticated user, expiry and one-time state before any token request; token exchange uses the callback captured when the flow began.
- Promo codes are hashed server-side. Redemption requires authentication and CSRF, permits five attempts per five minutes, and grants lifetime access transactionally under the same user lock as payment settlement. Unique redemption records prevent duplicate grants; optional expiry/usage limits and disabled codes are enforced under a code lock. Codes are not rendered in frontend HTML or activity logs.
- Automatic mode enables discovery, matching and preparation without raising the user's daily send limit or bypassing factual review, eligibility, expiry or recipient checks. Existing jobs wait for a verified career profile and configured AI before being queued. A full-worker heartbeat is distinct from discovery-only processing.
- Document file modes accept only `0600` (default) or `0640` for a private shared worker/web group or named ACL. World-readable document modes are rejected. The local deployment grants only the worker and Apache users access; serving files still checks account ownership.
- Legacy local PDF and raster-image responses require authentication and document ownership, and allow framing only from the same origin through `X-Frame-Options: SAMEORIGIN` and CSP `frame-ancestors 'self'`. Application pages retain `DENY`/`frame-ancestors 'none'`; ordinary local downloads retain the sandbox policy, and DOCX files are always attachments. The in-app PDF reader uses pinned local PDF.js assets, same-origin workers and canvas/text layers. It follows the ownership-checked download redirect with same-origin credentials and no referrer, so cloud requests carry no application cookies or authorization headers. PDF scripting and XFA are not enabled; the CSP retains its restrictions on inline scripts and evaluation.
- Cloud documents remain in a private bucket with uniform access and public access prevention. The service-account key stays server-side at its configured path. Account- and CSRF-checked upload reservations sign only an exact object, MIME type and byte length, expire after 15 minutes, and require generation zero to prevent overwriting an object. Finalization verifies cloud metadata, pins its immutable generation, and creates one account-owned record under a transaction. Workers validate actual file contents before extraction or application processing. Views/downloads check ownership before issuing a five-minute signed URL; possession of that short-lived link grants access until it expires. URLs are not cached or logged. CORS is limited to configured browser origins, and browser cloud transfers omit application cookies. Migrations verify checksums and retain a private recovery manifest; local copies require a separate explicit cleanup operation.
- The stateless document renderer uses a server-only bearer secret, constant-time authentication, bounded JSON/ZIP/XML inputs, exact paragraph targets and one conversion at a time. It rejects macros, embedded objects, unsafe paths, external media and active XML. Word conversions use unique temporary directories/profiles; HTML scripts and network requests are blocked. Payloads/tokens are not logged, and temporary files are removed after requests. The Cloud Run runtime identity receives access only to its renderer secret. PHP retains ownership, entitlements, review, approval and submission rules. PDF previews/exports are authenticated and rate limited.
- Public structured vacancy parsing recognises only explicit CV/application-to-email instructions with one unambiguous advertised address. Company enquiry emails and multiple possible recipients remain external applications. An explicit earlier closing date takes precedence over later listing metadata.
- Manual-application alerts use PHPMailer with authenticated SMTP, forced STARTTLS/SMTPS and peer/name certificate verification. SMTP credentials stay in the server environment, debug output is disabled and provider error text is never returned or logged. Recipients come from the authenticated account record, not CV text, advertisements or client-supplied email fields. Job text is HTML-escaped; only HTTP(S) employer links without embedded credentials/control characters are displayed, and none are fetched. CVs and letters stay behind authenticated ownership checks. Unique per-account/job outbox records and one-attempt send tasks prevent automatic replay of confirmed or uncertain sends; alert delivery never creates an application submission.
